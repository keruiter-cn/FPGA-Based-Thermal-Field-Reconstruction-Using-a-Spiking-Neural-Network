# 04 UDP 接口、字节布局与系统联调

## 适用范围与用法

用于将算法数据真正送到FPGA并还原输出，覆盖硬件接收/发送、DDR装载、输入缓存和主机通信。输入需包括RTL收发接口、应用数据格式、位流/权重版本与主机代码。先定义双向字节契约，再使用 [transport_codec.py](scripts/transport_codec.py) 的纯函数验证；工具不发送网络数据。

## 工作流

1. 分清tensor元素顺序、硬件word/lane排列、应用字节流、UDP包分块四个层级。为每个方向给一个非重复字节模式，不用全0数据验证字节序。
2. 为“权重→输入→计算→输出”定义合法阶段、预期总字节、完成条件与恢复入口。输入不是图像文件，而是编码后的多个时间步；输出也不是同格式回显。
3. 先用已知数据测试收发路径，再连接真实模型。每一层记录发送长度、接收长度和首尾字节，最后再检查数值尺度。
4. 接收端以完整应用帧为单位聚合。检查源地址、包长、超时与当前会话；如需可靠重排/续传，先设计session/frame/packet序号和校验，不能给旧协议单方面加主机重试。
5. 将字节转换做成可单测的纯函数，socket生命周期与GUI分离。错误后停止本批，按明确恢复流程重置硬件阶段，避免混入上一帧。

## 项目案例

- 主机 `configure_socket()` 的本地模式为PC `192.168.137.1:6001`、FPGA `192.168.137.2:6002`，对应 `rtl/eth/eth_top.v`；收发主体是 `eth_receive.v/eth_transmit.v`。先核对PL网口、ARP、DDR校准、协议阶段，再讨论模型结果。
- UNET权重13963328字节，输入200×200×3×4=480000字节，输出200×200×4=160000字节。`send_num=512` 沿用hex字符数含义，实际发送256字节；接收每包1280字节，两方向不相同。
- `pre_process/reverse_data.py` 的权重转换是：512位拆两个256位半块，先发高半块；每半块内保留64位lane顺序，但lane内字节逆序。不能将其简化为整个64字节倒序。新增工具以实际两份权重核对全部块。
- 回包按小端**完整有符号32位**解析。主机最终尺度为 `acc/3/4096*2+298`；MAT的 `u` 已是目标参考尺度，不能再次加298。`pe.v` 与末层写回路径是符号语义依据。

```powershell
python skill/udp-integration/scripts/transport_codec.py --original file/weight/unet_weights.txt --transmitted file/weight/unet_weights_reverse.txt
```

## 踩坑、验证效果与失效条件

源码明确记录了负累加误解码风险；以-1、-12288和int32边界验证补码，避免将符号位当成26位或直接裁剪负数。现有主机在坏包/超时后抛错，原因是无板端帧号，直接续拼无法保证身份。主机按接收顺序生成的frame_id仅用于UI关联。

本次测试了权重重排的已知模式、逆变换和当前实际权重全块比对，输入pair打包、负数输出解码及长度反例；没有发送真实UDP或重新上板。新协议采用不同位宽、压缩、包头或板端排序时，必须改转换与契约；当前工具不验证网络丢包、交换机MTU或DDR状态机。
